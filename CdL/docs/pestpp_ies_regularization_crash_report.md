# pestpp-ies: heap-corruption crash in the regularized IES upgrade at large ensemble size

**Component:** `pestpp-ies` (PEST++ suite) — **not** pyemu. pyemu (`pyemu.os_utils.start_workers`)
only launches the `pestpp-ies` master process and reports its non-zero exit; the crash is inside
the compiled `pestpp-ies` executable.

**Version:** pestpp-ies 5.2.27 (win64). Driver: pyemu 1.4.0, Python 3.12, Windows Server 2025.

---

## Summary

When Tikhonov regularization is active (`ies_reg_factor > 0`, with a large set of first-order
prior-information equations) **and** the ensemble is large (`ies_num_reals = 150`), the
`pestpp-ies` **master process crashes during the iteration-1 upgrade step** with Windows exit
status **`0xC0000374` (STATUS_HEAP_CORRUPTION)**. All forward model runs complete successfully;
the crash is in the master while it collates the upgrade ensembles / composite phi.

Crucially this is **heap corruption (a memory-safety bug), not out-of-memory** — at the moment of
the crash the machine had **127 GB / 137 GB RAM free (7 % load)**.

## Configuration that triggers it

- Adjustable parameters: 257 (Kh pilot-point multipliers + BC scalars)
- Observations: 11 638 (4 358 nonzero-weight)
- **Prior-information equations: 8 528** — first-order (preferred-difference) Tikhonov on the
  pilot points, generated by `pyemu.helpers.first_order_pearson_tikhonov`, group `regul_cc`
- `++ies_reg_factor(0.5)`, `++ies_num_reals(150)`, `++ies_autoadaloc(true)`,
  `++ies_parameter_ensemble(prior_pe.jcb)`

## Reproduction matrix (same model/pst; only these knobs changed)

| `ies_reg_factor` | `ies_num_reals` | Result |
|---|---|---|
| 0.0 (off) | 150 | **OK** — 3 iterations, ~45 h, clean |
| 0.5 | 30 | **OK** — completes |
| 0.5 | 150 | **CRASH** — `0xC0000374` during the iteration-1 upgrade |

So the crash requires **regularization on AND a large ensemble**. Regularization alone (30 reals)
is fine; a large ensemble alone (reg off, 150 reals) is fine. The two together fail.

## Where it dies

The record file's last entries before the crash are in the upgrade step:

```
  ---  running upgrade ensembles  ---
...3 inflation factors (lambdas) times 3 backtracking factors times N realizations ...
...making runs                       <- all these model runs SUCCEED (0 failures in the .rmr)
[master crashes here, during collation / composite-phi evaluation of the upgrade ensembles]
```

`pestpp-ies` reports the composite phi (measurement + regularization) is computed over every
realization for every lambda × backtracking trial. The work scales roughly with
**`n_reals × n_prior_info`** ( = 150 × 8 528 ≈ 1.3 M reg-residual evaluations per trial), versus the
working 30-real case (30 × 8 528 ≈ 0.26 M).

## Hypothesis (black-box; not from source inspection)

A buffer used in the regularization-phi accumulation over the upgrade ensemble is likely sized
from `n_reals` and/or `n_prior_info`, and at large size an **out-of-bounds write or a 32-bit index
overflow** corrupts the heap. Candidate areas for the maintainers to audit:

- the composite/regularization `L2PhiHandler` accumulation over the upgrade ensemble;
- any pre-sized matrix/vector indexed by `(realization × prior_information)`;
- index types in that loop (ensure `size_t`/64-bit, not `int`).

## Suggested fixes

1. **Root cause:** add bounds checking and 64-bit indexing in the regularized composite-phi
   computation for the upgrade ensembles; reproduce under a heap validator (AddressSanitizer /
   Application Verifier / Dr. Memory) with the config above.
2. **Robustness / mitigation:** compute the regularization phi **sequentially (streamed per
   realization)** and accumulate, instead of materializing a large `(reals × prior_info)`
   structure — lowers peak allocation and likely sidesteps the faulty path.
3. Optionally cap or warn when `n_reals × n_prior_info` exceeds a safe threshold.

## Current workaround (user side)

Reduce the number of prior-information equations so `n_reals × n_prior_info` stays below the level
that runs clean: raise the `abs_drop_tol` of `first_order_pearson_tikhonov` (0.20 → 0.60) to keep
only the closest-neighbour smoothness pairs (~8 500 → ~1–1.5 k equations). This retains the full
150-real ensemble and the smoothness regularization while avoiding the crash. Alternatively,
reduce `ies_num_reals`.
