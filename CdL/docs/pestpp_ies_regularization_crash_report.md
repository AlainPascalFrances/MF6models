# pestpp-ies: heap-corruption crash in the threaded automatic-localization (autoadaloc) upgrade

**Component:** `pestpp-ies` (PEST++ suite). pyemu (`pyemu.os_utils.start_workers`) only launches
the `pestpp-ies` master and reports its non-zero exit; the crash is inside the compiled
`pestpp-ies` executable.

**Version:** pestpp-ies 5.2.27 (**win64**). Driver: pyemu 1.4.0, Python 3.12, Windows Server 2025.

> **Correction (this report was revised).** An earlier version of this report speculated that the
> crash came from the regularization / composite-phi computation over the prior-information (Tikhonov)
> equations. That mechanism is wrong: pestpp-ies does not use prior-information equations in the IES
> objective (users' manual, regularization section). The reproducible evidence below points instead at
> the **automatic adaptive localization (`autoadaloc`) upgrade solve**, with the prior-information-equation
> *count* acting only as a size lever. The mechanism here is a **direction inferred from black-box
> behaviour**, not from source inspection.

---

## Summary

The `pestpp-ies` **master process** heap-corrupts (**Windows exit `0xC0000374`,
STATUS_HEAP_CORRUPTION**) during the **iteration-1 upgrade**, in the **threaded automatic-localization
solve**, when `ies_autoadaloc` is on, the control file carries a **large set of prior-information
equations**, and the ensemble is large (`ies_num_reals = 150`). All forward model runs complete
(0 failed runs in the `.rmr`); it dies in the master, not a worker.

This is **heap corruption, not out-of-memory** — the machine had **127 GB / 137 GB RAM free (7 % load)**
at the crash.

## Where it dies

The last coherent lines in the `.rec` before the crash are the localizer, not the objective:

```
...preparing fast-lookup containers for threaded localization solve
...starting calcs for glm factor 10
...starting calcs for glm factor 100
...starting calcs for glm factor 1000
  ---  running upgrade ensembles  ---
[master crashes]
```

`autoadaloc` also emits `Note: N observations have no nonzero entries in autoadaloc localizer`, and the
prior-information equations are parsed (`Number of prior estimates = 8528`).

## Reproduction (same model & control file; only these two knobs changed)

- 257 adjustable parameters, ~11 638 observations (4 358 nonzero-weight), `ies_num_reals = 150`,
  14 local PANTHER workers.
- The prior-information equations are first-order (preferred-difference) Tikhonov on the Kh pilot
  points, generated by `pyemu.helpers.first_order_pearson_tikhonov`, group `regul_cc`.

| prior-information eqs in the .pst | `ies_autoadaloc` | result |
|---|---|---|
| 0 | true | **OK** — 3 iterations, ~45 h, clean |
| ~8 500 | true | **CRASH** — `0xC0000374` in the localized upgrade |
| ~1 240 | false | **OK** |

So a run that went 45 h cleanly at 150 realisations with `autoadaloc` **on** began heap-crashing once
~8 500 prior-information equations were added to the control file (`autoadaloc` still on), and turning
`autoadaloc` off resolved it. The prior-information count is a **size lever** that flips the crash
on/off; the faulting path is the localizer.

## Hypothesis (black-box; not from source inspection)

The automatic-localizer construction / threaded localized-upgrade solve appears to pull the
prior-information rows into its threaded, shared containers, and overruns or races when that set is
large. Candidate areas for the maintainers to audit:

- how `autoadaloc` sizes and fills its localizer containers when prior-information equations are present
  in the control file (are they counted as observations?);
- bounds checking / 64-bit indexing and any data race in the threaded localization solve
  (`preparing fast-lookup containers for threaded localization solve`).

## Platform note

Reproduces on **Windows (x64)** only in our hands. A heap overrun / data race in threaded container
access is often allocator/platform/timing specific, so a clean run under a macOS (ARM) heap validator
at comparable problem sizes is consistent with this. We can try to catch it under Application Verifier
or Dr. Memory on Windows if that would help.

## Workaround (user side)

Run with `ies_autoadaloc` **off** when a large prior-information set is present; and/or keep the
prior-information-equation count modest (here, raising `first_order_pearson_tikhonov`'s `abs_drop_tol`
from 0.20 to 0.60 cut ~8 500 → ~1 240 equations). Either avoids the crash at 150 realisations.
